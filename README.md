## **★  병목을 어떻게 찾고 대규모 트래픽에 어떻게 대응해야할까?**

**TPS(Transaction Per Second)**  1초당 처리한 트랜잭션의 수 : DB

**RPS=HTTP 요청 수/측정시간(초)
RPS(Requests Per Second)**는 1초 동안 서버가 받은 HTTP 요청 수 : HTTP

| 구분 | Request | Transaction |
| --- | --- | --- |
| 기준 | 서버에 들어온 개별 요청 | 논리적으로 완료된 업무 |
| 대표 지표 | RPS | TPS |
| 예시 | `POST /orders` 호출 | 주문 한 건 완료 |
| 실패 처리 | 개별 요청 단위 | 전체 작업 Commit·Rollback |
| 관계 | 하나의 업무에 여러 요청 가능 | 여러 요청을 묶어 하나의 업무가 될 수 있음 |

일반적인 API 트래픽은 RPS로, 주문·결제 같은 업무 처리량은 TPS

**★ 병목 현상 찾는 법 :**

1. **RPS·TPS**
2. **P95·P99 응답시간**
3. **4xx·5xx·Timeout**
4. **ALB TargetResponseTime과 Target 5xx**
5. **Pod CPU·메모리·Throttling·재시작**
6. **HPA·Pending Pod·노드 자원**
7. **DB cpu/memory Connection·Query Latency·Lock**

## **★** 개발 생산성을 높이려면 어떤 업무를 해야할까?

개발자는 인프라를 몰라도 필요한 환경을 빠르게 생성, 배포가능하도록 구성해야 생산성 올라

현재 이 업무를  플랫폼이 해주고 있음.

- 표준 Code 환경, 이미지 자동 빌드와 배포 설정을 해놔서 개발자가 코드 수정 시 이미지를 만들어 자동 배포되도록 설정
- OOM / CPU Throttling이 발생하지 않도록 스펙 조정
- 빠른 장애 대응
- 반복 장애는 문서
- 개발자가 직접 메트릭 볼수 있는 권한 부여

## **★** 어떻게 성능 개선?

- CPU·메모리,응답 시간,오류율,사용률과 같은 핵심 지표를 모니터링해 정상 상태의 기준 샘플
- 병목을 찾아 Pod Right-Sizing, HPA, Readiness Probe 등을 개선하고, 배포 시에는 Canary 방식과 자동 롤백으로 장애 영향을 최소화
- 장애 발생 후에는 원인과 대응 과정을 문서화

## 모니터링해 정상 상태의 기준 ?

1. 응답 시간: 평소 P95보다 일정 비율 이상 증가
2. 오류율: 정상 범위를 벗어나거나 SLO 초과
3. CPU: 70~80%가 일정 시간 이상 지속
4. 메모리: OOM 발생 가능성을 고려해 Limit의 80% 이상 지속

## **★ 비용 최적화는 어떻게 했나?**

프로젝트 시작 후 실제 EKS에 배포되어있는 사용량보다 너무 많은 리소스가 할당되어있어 **유휴 자원** 확인. **3개월 치의 실제 CPU/Memory 사용량 분석** → **CPU Request 평균 값의 * 1.2**, **Limit은 제한X**. **memory request는 P95** **Limit은 max의 1.2로* 하고 **모니터링하며 수치를 수정**.

## **★ CPU/memory request/limit 왜 이런 값을 두었나요?**

평소에는 사용량이 낮음, API 호출 시 사용량 발생하기때문, **순간 피크를 고려하되 유휴자원 발생 방지하도록 CPU Request는 평균 사용량에 여유분**을 더하고, **CPU 스로틀링 방지 위해 Limit제거**,메모리는 **memory request는 OOM 위험 때문에 P95** 기준으로 설정했습니다. **Limit은 OOM 방지를 위해 max값** 최대 사용량을 참고해 여유를 둠

## **★ 2. Gitops 개인프로젝트**

회사에서 Terraform, GitOps, Istio를 구축할 기회가 제한적이어서 개인 프로젝트로 진행했습니다.

먼저 Terraform으로 AWS의 VPC, Subnet, Security Group, EC2 Master·Worker 노드, ECR, IAM Role을 구성했습니다. GitHub Actions이 **Access Key 없이 AWS에 접근하도록 OIDC 기반 임시 권한을 적용했고, 서버 관리는 SSH 대신 SSM Session Manager**를 사용했습니다.

EC2에는 **kubeadm과 containerd**로 Kubernetes 클러스터를 구성하고,helm으로 **Argo CD와 Istio** 를 배포했습니다.

코드가 **master 브랜치에 Push**되면 **GitHub Actions이** Docker 이미지를 빌드해 **ECR에 Push** 이후 별도로 분리한 **GitOps 설정 저장로의 이미지 태그와 배포 메타데이터를 변경해 다시 Push하도록 구성**했습니다.

**Argo CD는 GitOps 저장소의 Kustomize 운영 Overlay를 감시하고 변경 사항을 Kubernetes에 자동 동기화**합니다.

Istio에서는 하나의 공통 Service 앞에 DestinationRule을 구성해 version: v1, version: v2 라벨을 각각 Subset으로 분리했습니다. VirtualService에서는 처음에는 v1 90%, v2 10%로 소량의 트래픽만 신규 버전에 전달하고, 검증 과정에서 70:30처럼 비율을 확대하는 카나리 배포 방식을 경험

문제가 발생하면 비율을 v1 100%, v2 0%로 변경해 즉시 롤백할 수 있도록 했습니다.

마지막으로 Istio Sidecar 자동 주입과 PeerAuthentication STRICT를 적용해 Gateway부터 애플리케이션 Pod까지 mTLS 통신을 강제했습니다.

이 프로젝트를 통해 인프라 구축부터 CI, GitOps CD, 카나리 배포, 트래픽 롤백까지 전체 배포 과정을 직접 설계하고 검증했습니다.

## **★ Istio 구성한 목적과 자세히 설명**

Istio는 신규 버전을 안전하게 배포하고, 서비스 간 통신을 보호하기 위해 구성, destination rule에서 deployment를 v1,v2로 subset을 구성, virtual service로 트래픽 제어하여 카나리 배포 구조, mTLS peerauthentication STRICT 모드 설정

**STRICT** 모드는 모든 트래픽에 mTLS를 강제하고, **PERMISSIVE** 모드는 비인증 트래픽을 허용해 마이그레이션을 지원합니다.
